## 1. Intended flow (as specced)

Oracle runs `oracle-startup`, detects `AUTO_FLOW` from user keywords, compacts and routes via `$UB talia "/compact" --next "/<skill>"` — it never stays alive to orchestrate. Alfred refines A/Cs (Stage 1 of 5, inception gates never skipped) and under `AUTO_FLOW` self-routes to Dupin. Lucius blueprints the epic and emits a `Stories` block (`depends_on`/`moscow`/`type: test` E2E story; `templates-shared.md` defines the `## Story Dependencies` table Dupin's phase scan reads). Dupin (always `AUTO_FLOW`) discovers stories/ACs, builds epic + story branches, then loops 3a(scan) → 3b(merge) → 3c(re-scan) → 3d(dispatch) → 3e(handoff) → 3f(progress) → 3g(checkpoint → Talia self-queue), dispatching `dup-ac-implement` / `dup-ac-commit` / `dup-ac-qa` / `dup-ac-pr` subagents under `MAX_CONCURRENT_AGENTS=5`, with one claim per AC, 15-minute liveness leases, per-AC handoffs at `handoffs/dupin/<STORY>/<stage>-<STORY>-AC<n>.md`, and a 3-stage chain `impl → qa → commit`.

### P0 — stuck-pipeline / silent-corruption risks
1. **Explicit claim release at stage completion** (G5). **Today:** claims are only freed when liveness decides the agent is *dead* (stale > 15 min with no live task evidence) — a cleanly finished AC keeps its claim for up to the full TTL. **Failure mode:** within that window `claim-ac --check` reports conflict, so Dupin either skips re-dispatch of a genuinely open AC or counts a phantom occupied budget slot; the 37 stale-claim files are the accumulated result. **Fix:** Dupin 3b (merge-confirmed) runs `claim-ac --release <ac_id>` for each merged AC, and `cleanup_dead_claims` additionally releases claims whose AC has a complete `impl→qa→commit` chain or is in `acs_merged[]` (the backstop). **DONE 2026-08-21:** both implemented — `release_merged_claims()` backstop wired after the auto-heal sweep; 3 tests pass; 37 stale claims clear on next global scan.
2. **Handoff schema validator** (G6). **Today:** `make-handoff` silently fills missing required fields with `N/A`, so subagent handoffs can land as `Status: N/A` / `Repo Root: N/A`. **Failure mode:** the scanner treats such files as "exists but incomplete" and loops on them across cycles instead of failing loudly once. **Fix:** in `make-handoff.py` `_post_write` (or a PostToolUse hook), validate subagent-mode required fields (`repo`, `ac_selected` must not be N/A) and that `_qa`/JSON fields parse as JSON; warn at minimum. **DONE 2026-08-21:** required fields now hard-fail on empty/`N/A` (Route To / Ticket Status exempt); N/A `Repo Root` rejected, corrected payload writes.
3. **One liveness signal per claim** (G5 tail). **Today:** four claims (LOC-0074-AC1/2/3, LOC-0075-AC3) share one `task_id`, so a single heartbeat gates four budget slots. **Failure mode:** one dead process silently frees four slots at once (or one live process keeps four slots alive when only one is real). **Fix:** `--update-task-id` writes the real per-agent task id per claim; the scanner warns when N claims share one `task_id`. **DONE 2026-08-21:** the launch sequence (`claim-ac` → `Agent()` → `--update-task-id` → `register-heartbeat-session`) was already specced and enforced by the launch-verification gate; the missing half is now in — `find_shared_task_ids()` in `check-agent-progress.py` surfaces `shared_task_ids` in both `concurrency` and `dispatch_budget` (2+ slots on one task_id = one heartbeat gating N slots). Unit-tested; live global scan verified.

### P2 — observability / hardening
10. **Auto audit-log entries for subagent handoffs** (G11). **Today:** the audit log holds 24 entries for a 94-AC epic and its role names don't match the allowlist scheme, so the `audit-log query` resolution path is hollow. **Failure mode:** subagents can't resolve ambiguity from history; post-mortems have no reliable timeline. **Fix:** make-handoff appends the `RESULT:` line itself for `dup-ac-*` types and validates the role ID format. **DONE 2026-08-21:** RESULT entry appended with validated subagent role (regex fallback to handoff type); both entries verified in audit.md.
11. **Configurable budget.** **Today:** `MAX_CONCURRENT_AGENTS` is a constant in `check-agent-progress.py`. **Failure mode:** tuning concurrency requires editing tool source. **Fix:** expose it as an env var and document it in the dupin SKILL. **DONE 2026-08-21:** owner asked "will that even work" — answer: a plain env var only reaches a tool if it's in the Claude Code process's environment (Windows: setx + restart, or an inline `MAX_CONCURRENT_AGENTS=8 $UB ...` prefix per call); an `export` in one Bash call does NOT persist to the next. ## 4. Case study: why the per-AC worktree flow drifted the Black_Owned repo — verdict recorded 2026-08-22 (#68)

Owner hypothesis, **confirmed [HIGH]**: the per-AC worktree flow (Dupin convention `.worktrees/{STORY_KEY}-AC<n>`) was the primary cause of the design drift documented in `Black_Owned/docs/design-drift-audit-2026-08-20.md`. The deeper failure: each AC merged from its own stale snapshot, and no integration verification ran against the integrated tree between merges.

| Finding class (Black_Owned audit) | Attributed cause |
|---|---|
| Three competing `scrape_jobs` schemas, dual schema sources of truth (runtime `CREATE TABLE IF NOT EXISTS` vs migrations), split status enums, `chat_messages` vs `messages`, dead/orphan routes, port-9000 collision | Independent per-AC worktrees each creating the same seam from its own assumption; merges never compared them |
| QA spec pinning a broken nats healthcheck | The spec validated the worktree's snapshot, not the integrated system |
| Blueprint/README drift (ClickHouse-centric docs vs Postgres reality) | Docs not updated in the same merge as the behavior change; predates and amplifies the above |
| Fabricated `pending_import` source data (#49 rejection, 2026-08-22) | Data provenance — unrelated to worktrees |
| Unbuilt features (chat, claim wizard, dashboards) | Scope never built — not parallelism |

**Mechanism:** (1) ACs branched at different moments, so two ACs could each "create" the same table/enum without either seeing the other; (2) merges were per-AC and mechanical — the full suite never ran against the integrated tree, so conflicts surfaced only at audit time; (3) runtime `CREATE TABLE IF NOT EXISTS` bootstraps were a *symptom* — worktrees could not trust shared DB state, so every module bootstrapped its own; (4) worktrees make forking divergent copies of compose/env cheap — that is how the port collision and the healthcheck drift happened.

**Fix protocol (binding for all follow-up work in this repo, and for future Dupin epics on it):**
1. **Merge discipline at seams.** Work touching shared seams (migrations, shared types, compose, API routes) is serialized — one AC at a time. Worktrees only for disjoint slices.
2. **Integration is the gate.** Per-AC unit tests are necessary, insufficient: after every merge the full gate (tsc + full jest + live-stack e2e where relevant) must pass before the next AC starts.
3. **Structural single-sourcing (done 2026-08-21):** migrations own schema (Fix 7), one status enum (Fix 2), one `scrape_jobs` table (Fix 6); contract specs pin the seams.
4. **Assert behavior, not implementation strings.** Boundary specs assert outcomes ("a healthcheck is defined", "the health endpoint returns ok"), not exact command text; live behavior belongs in e2e against the running stack. Applied to the nats compose spec 2026-08-22 (it previously pinned the broken probe, then the good one — both are implementation strings).
5. **Drift audit as a scheduled gate** after every epic; blueprint/README updated in the same merge as the behavior change.
6. **Worktrees where they are harmless** (isolated UI/component work); never for shared schema/config.
